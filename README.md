# DocQuery

Upload a PDF, TXT, or DOCX file and ask questions about it. Answers are
generated by an LLM (via Groq) grounded only in retrieved excerpts from your
documents, with real citations (filename, page, and excerpt) shown alongside
every answer.


## Requirements

- Python 3.11+
- A [Groq API key](https://console.groq.com) (free tier is fine)
- ~500 MB free disk space (the local embedding model downloads on first use)

## Installation

macOS/Linux:
```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# edit .env and set GROQ_API_KEY=...
```

Windows (PowerShell):
```powershell
py -m venv venv
venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
# edit .env and set GROQ_API_KEY=...
```
If PowerShell blocks the activation script, either run
`Set-ExecutionPolicy -Scope Process RemoteSigned` first, or just use
`venv\Scripts\activate.bat` from `cmd.exe` instead. If `python`/`python3`
isn't recognized but `py` is, use `py` for every command above (Windows'
official launcher, not the Microsoft Store alias).

## Running

```bash
python -m backend.main
```
(Use `python3` instead of `python` on macOS/Linux if that's what your system uses.)

Then open **http://127.0.0.1:8080** in a browser. That's it — one command
starts the API *and* serves the dashboard and chat pages from the same
process/port, so there's nothing separate to run or configure. (The old
version of this project required a second, separate Flask process just for
the contact form; that's been merged in.)

On first use, the embedding model (`sentence-transformers/all-MiniLM-L6-v2`,
~90 MB) downloads automatically from Hugging Face and is cached locally.
This requires outbound internet access the first time only.

## Environment variables

See [`.env.example`](./.env.example) for the full list with defaults. Only
`GROQ_API_KEY` is required; everything else (chunk size, retrieval settings,
upload limits, storage paths, the contact form's SMTP settings) has a
working default and can be left alone.

## Supported files

| Format | Notes |
|---|---|
| `.pdf` | Text-layer PDFs. Page numbers are preserved for citations. Scanned/image-only PDFs are detected and reported as "no searchable text found" rather than silently indexed as empty. |
| `.txt` | UTF-8 by default, with automatic encoding detection as a fallback for other common encodings. |
| `.docx` | Headings, paragraphs, and tables are extracted with their structure preserved (heading text becomes the "section" shown in citations). |

Max upload size defaults to 10 MB (`MAX_UPLOAD_SIZE_MB` in `.env`), enforced
on the server — not just in the browser.

## RAG architecture

```
Upload → extract text (per format) → detect empty/unreadable → chunk
       → embed locally (MiniLM) → store in Chroma (tagged with document_id,
         filename, page/section, chunk_id)

Ask → (if follow-up) condense question using recent conversation history
    → embed the question → retrieve top-K chunks (optionally filtered to
      one document_id) → drop low-relevance/over-represented chunks
    → build a grounded prompt (system instructions + numbered context +
      question + recent conversation) → Groq LLM → answer
    → return answer + structured citations (filename, page, excerpt)
    → persist both turns to the conversation's history (SQLite)
```

- **LLM**: Groq-hosted, model configurable via `GROQ_MODEL` (default
  `openai/gpt-oss-20b` — Groq's recommended replacement after
  `llama-3.1-8b-instant` was deprecated; see [Troubleshooting](#troubleshooting)
  if you hit a `model_not_found` error).
- **Embeddings**: local, via `sentence-transformers/all-MiniLM-L6-v2` — no
  embedding API calls or per-query cost.
- **Vector store**: Chroma, persisted to `./chroma_db`, one collection with
  every chunk tagged by `document_id` so searches and deletes can be scoped
  precisely to one document without touching any other.
- **Chunking**: character-based (`RecursiveCharacterTextSplitter`),
  `CHUNK_SIZE`/`CHUNK_OVERLAP` configurable, default 500/100.
- **Retrieval**: top-`TOP_K` (default 4), with a distance threshold and a
  per-document cap so a handful of near-duplicate chunks from one file can't
  crowd out everything else when asking across multiple documents.
- **Conversation memory**: the last `MAX_HISTORY_TURNS` turns (default 5)
  are kept and used both for follow-up question understanding and as
  context for the LLM — bounded, not unlimited history.
- **Streaming**: `/api/conversations/{id}/ask/stream` streams the answer via
  Server-Sent Events. The frontend automatically falls back to the regular
  non-streaming endpoint if the stream can't be opened.

## Project structure

```
backend/
├── main.py              # FastAPI app: startup, CORS, error handlers, static hosting
├── config.py             # every setting, read from the environment
├── database.py           # SQLite: document metadata + conversations/messages
├── models/schemas.py      # request/response models
├── routes/                # documents.py, chat.py, contact.py, misc.py
├── services/
│   ├── document_service.py   # PDF/TXT/DOCX loaders + chunking
│   ├── embedding_service.py  # embedding model (singleton)
│   ├── vector_store.py       # Chroma add/search/delete
│   ├── rag_service.py        # retrieval, prompting, streaming
│   └── email_service.py      # contact form (merged from the old app.py)
└── utils/
    ├── file_utils.py      # filename/size/type validation, no path ever
    │                        built from a client-supplied filename
    └── errors.py           # structured {"success": false, "error": {...}} responses

frontend/
├── index.html            # dashboard: upload + document management
├── chat.html              # chat + evidence panel + document scope
├── config.js               # the one place the backend URL is defined
└── src/                   # api.js, theme.js, components.js, styles.css

tests/                      # pytest suite, runs fully offline (see below)
```

## API endpoints

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/documents` | POST | Upload a file |
| `/api/documents` | GET | List documents |
| `/api/documents/{id}` | GET | One document's metadata |
| `/api/documents/{id}/download` | GET | Download the original file |
| `/api/documents/{id}` | DELETE | Delete a document + its chunks |
| `/api/conversations` | POST | Start a new conversation |
| `/api/conversations` | GET | List conversations |
| `/api/conversations/{id}` | GET | A conversation's messages |
| `/api/conversations/{id}` | DELETE | Delete a conversation |
| `/api/conversations/{id}/ask` | POST | Ask a question (JSON response) |
| `/api/conversations/{id}/ask/stream` | POST | Ask a question (SSE stream) |
| `/api/contact` | POST | Send a contact-form message |
| `/api/settings` | GET | Current (read-only) configuration |
| `/api/health` | GET | Health check |

Every error response has the same shape:
`{"success": false, "error": {"code": "...", "message": "..."}}`.

## Development / testing

```bash
pip install -r requirements-dev.txt
pytest
```

The test suite (33 tests) runs **fully offline**: the real embedding model
and the real Groq API are both replaced with small, deterministic fakes
(see `tests/conftest.py`), so it never needs network access or an API key.
That means it thoroughly verifies the *pipeline* — upload, chunking,
storage, retrieval, filtering, citations, deletion, persistence across a
simulated restart, conversation memory, streaming — but it does **not**
prove the real MiniLM model or the real Groq API behave a particular way.
Do one real upload and one real question with a valid `GROQ_API_KEY` before
relying on this beyond local testing.

## Troubleshooting

- **`model_not_found` / "The model `...` does not exist or you do not have
  access to it"** — Groq retired the model your `.env` points at. Set
  `GROQ_MODEL=openai/gpt-oss-20b` (the current default) or pick any model
  from [console.groq.com/docs/models](https://console.groq.com/docs/models),
  then restart the backend. This can't be caught at install time since it
  depends on Groq's live catalog, not on anything in this repo.
- **"GROQ_API_KEY is not set" / questions fail with `LLM_NOT_CONFIGURED`** —
  add a key to `.env` and restart. The server itself still starts without
  one so you can browse the dashboard; only asking questions needs it.
- **First question is slow** — the embedding model downloads (~90 MB) on
  first use and is cached after that.
- **Upload fails with "content doesn't look like a valid .pdf/.docx file"**
  — the file's extension doesn't match its actual content (a basic
  magic-byte check); re-check the file.
- **Contact form returns "not configured"** — set `SMTP_USERNAME`,
  `SMTP_PASSWORD`, and `RECEIVER_EMAIL` in `.env`. It's optional; the rest
  of the app works without it.

## Known limitations

- DOCX table position relative to surrounding headings is a reasonable
  approximation, not exact document order (python-docx doesn't expose true
  interleaved order without walking the raw XML body).
- No OCR — scanned/image-only PDFs are detected and reported clearly, but
  their text isn't extracted. The loader architecture (`backend/services/
  document_service.py`, one function per format) is set up so OCR could be
  added as another format-specific step later without restructuring anything.
- No user accounts — this is a single-shared-workspace app, matching the
  original project's scope. Every document and conversation is visible to
  anyone who can reach the server.
- Conversation "follow-up" understanding relies on an LLM rewriting the
  question before retrieval; like any LLM step, it can occasionally
  misjudge what a pronoun refers to.
- The streaming endpoint's plumbing (FastAPI → SSE → browser) is verified
  with automated tests, including a real run on a live machine — which
  caught a real bug: a mid-stream LLM failure was crashing the connection
  with no signal to the UI (see the [CHANGES report](./CHANGES.md) addendum
  for the fix). Real token-by-token *content* from a successful live Groq
  call hasn't been separately confirmed yet, since that run hit the model
  error before generation started; the plumbing itself has now been proven
  live, including its failure path.

## Development notes

- All configuration lives in `backend/config.py`, read from the
  environment — nothing important is hardcoded in routes or services.
- Nothing on startup ever deletes existing data; `backend/database.py` and
  `backend/config.py` only ever *create* storage if it's missing.
- Every uploaded file is stored on disk under a server-generated name
  (`{document_id}{extension}`) — the client-supplied filename is kept only
  as a display label and is never used to build a filesystem path.
